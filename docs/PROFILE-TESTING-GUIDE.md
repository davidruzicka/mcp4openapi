# Profile Testing Guide

This guide explains how to write and run automated tests for your MCP profiles using the schema-driven testing framework.

## Overview

We use data-driven tests defined in `*.test.json` files alongside your profile definition. This allows you to:
- Verify tool behavior without a real API (using mocks).
- Enforce full coverage of all tool actions.
- Ensure critical security features (like stripping metadata parameters) are working.
- Protect against regressions when updating profiles.

## Quick Start

1. Create a test file named `profiles/<name>/profile.test.json`.
2. Add the schema reference and basic structure:

```json
{
  "$schema": "../../src/testing/test-schema.ts",
  "profile_name": "my-profile",
  "variables": {
    "projectId": "123"
  },
  "scenarios": [
    {
      "name": "List Items",
      "tool": "manage_items",
      "arguments": { "action": "list", "project_id": "{{projectId}}" },
      "mocks": [
        {
          "operationId": "listItems",
          "response": {
            "body": [{ "id": 1, "name": "Test Item" }]
          }
        }
      ],
      "expect": {
        "success": true,
        "result": [{ "name": "Test Item" }]
      }
    }
  ],
  "coverage": {
    "require_all_actions": true
  }
}
```

3. Run tests:
   ```bash
   npm test
   ```

## Test File Structure

### Top-Level Fields

- **`$schema`**: Path to `src/testing/test-schema.ts` for IDE validation.
- **`profile_name`**: Must match the `profile_name` in your `profile.json`.
- **`variables`**: Global variables accessible via `{{varName}}` in arguments and expectations.
- **`scenarios`**: Array of test cases.
- **`coverage`**: Configuration for coverage enforcement.

### Scenarios

Each scenario tests one execution of an MCP tool.

```json
{
  "name": "Scenario Name",
  "description": "Optional details",
  "tool": "tool_name",
  "arguments": { ... },
  "mocks": [ ... ],
  "expect": { ... }
}
```

## Mocking

Mocks intercept outgoing HTTP requests generated by the tool. You can mock by `operationId` (recommended) or raw `path`/`method`.

### By Operation ID

Maps directly to the OpenAPI operation used by the tool.

```json
{
  "operationId": "getProject",
  "response": {
    "status": 200,
    "body": { "id": 1, "name": "My Project" },
    "headers": { "content-type": "application/json" }
  }
}
```

### By Path & Method

Useful for endpoints not in OpenAPI or complex matching.

```json
{
  "method": "GET",
  "path": "/projects/123",
  "response": { ... }
}
```

## Assertions

The `expect` block defines what constitutes a successful test.

### Result Verification

- **`success`**: `true` (default) or `false` (for error cases).
- **`result`**: Partial match. The actual result must contain these fields.
- **`result_exact`**: Strict deep equality match.
- **`error_code`**: Expected error code string (e.g. "Forbidden").
- **`error_message_regex`**: Regex to match error message.

```json
"expect": {
  "success": true,
  "result": {
    "id": 1
  }
}
```

### Request Verification

Verify that the tool constructed the correct HTTP request. This is critical for testing parameter aliases, filtering, and security rules.

**Simple match (single request):**

```json
"expect": {
  "request": {
    "method": "GET",
    "path": "/projects/123",
    "query": { "state": "opened" },
    "query_absent": ["action"], // Ensure 'action' param was stripped
    "headers": { "authorization": "Bearer test-token" }
  }
}
```

**Regex matching (advanced):**

You can use regex for flexible matching of paths, bodies, or headers.

```json
"expect": {
  "request": {
    "path_regex": "/projects/\\d+/issues",
    "body_regex": ".*\"secure_mode\":true.*"
  }
}
```

**Available regex fields:**
- `path_regex`
- `origin_regex`
- `headers_regex` (map of header name to regex)
- `query_regex` (map of param name to regex)
- `body_regex`

**Multiple requests (sequences):**

For composite tools or flows that make multiple calls:

```json
"expect": {
  "requests": [
    { "method": "GET", "path": "/step1" },
    { "method": "POST", "path": "/step2" }
  ],
  "allow_additional_requests": false
}
```

## Coverage Rules

The test loader enforces strict coverage to prevent gaps.

### `coverage` Configuration

```json
"coverage": {
  "require_all_actions": true,
  "skip_actions": {
    "tool_name.action_name": "Reason for skipping"
  }
}
```

- **`require_all_actions`**: If true, every action defined in the profile must have at least one test scenario.
- **`skip_actions`**: specific actions to exclude from coverage checks.

### Automatic Enforcement

Even if `require_all_actions` is false, the system enforces:

1. **Destructive Actions**: Any tool/action with "delete", "remove", "revoke", etc., **must** be tested or explicitly skipped. This prevents dangerous operations from going untested.
2. **Critical Features**: If a tool uses **Parameter Aliases**, **Proxy Downloads**, or **Metadata Parameters** (like `action`), you **must** include at least one scenario that asserts the request structure (`expect.request`). This ensures these complex transformations are verified.

## Best Practices

1. **Test Happy Paths**: Verify the tool works with standard inputs.
2. **Test Edge Cases**: Test missing optional parameters or specific flag combinations.
3. **Verify Request Shape**: Always use `expect.request` for tools that modify inputs (e.g. `metadata_params` like `action` should not be sent upstream).
4. **Use Variables**: Use `{{var}}` to keep tests DRY and readable.
5. **Mock Minimal Responses**: Only mock the fields your tool actually reads/needs.

## Running Tests

Run all tests:
```bash
npm test
```

Run only your profile tests:
```bash
npm test profiles/my-profile/profile.test.json
```

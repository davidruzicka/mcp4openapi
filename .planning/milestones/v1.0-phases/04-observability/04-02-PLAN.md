<objective>
Add GET /ready readiness probe endpoint alongside the existing GET /health liveness endpoint, and prevent /ready from creating high-cardinality Prometheus path labels.

Purpose: Operators need a readiness signal (at least one profile loaded) that is separate from the liveness signal (server process running). Kubernetes readinessProbe and load balancers require a dedicated /ready endpoint that returns 503 until the server can actually serve traffic.

Output:
- `/ready` Express GET route registered in http-transport.ts after `/health` (line ~1659)
- Returns 200 + `{ status: 'ready', profiles: N }` when `this.profileStates.size > 0`
- Returns 503 + `{ status: 'not ready', reason: 'no profiles loaded' }` when empty
- Uses same `mcpRateLimiter` as `/health` (unauthenticated - clientAuthGate is only in handlePost)
- Metrics recorded via `this.metrics.recordHttpRequest(...)` using `profileId: 'unknown', tenantId: 'none'`
- `normalizePath` in metrics.ts extended to recognize `/ready` as a known path (prevents `path="/ready"` cardinality from raw session IDs or trailing slashes)
- Integration tests covering: 200 ready, 503 not-ready, no-auth-header, /health regression
</objective>

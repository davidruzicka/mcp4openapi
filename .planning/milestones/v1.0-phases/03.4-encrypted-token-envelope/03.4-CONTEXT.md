# Phase 03.4: Encrypted Token Envelope — Context

**Gathered:** 2026-05-06
**Status:** Ready for planning
**Source:** Design plan (pre-planned via plan mode session)

<domain>
## Phase Boundary

Deliver AES-256-GCM encrypted token envelopes so OAuth clients survive server restarts in k8s
without re-authenticating. No persistent storage dependency (no Redis/Postgres).

The encrypted token is issued to the MCP client after OAuth. On restart, the client presents
the same token — gateway decrypts it, recovers session state (access token, refresh token, client
registration), and optionally refreshes the access token silently. Fully backward-compatible:
plain tokens (no `mcp4.v1.` prefix) continue to work as today.

This phase also delivers the shared `token-envelope.ts` module that Phase 5 (Upstream OAuth Proxy)
will reuse for outbound token encryption.

Out of scope: outbound/upstream token encryption (Phase 5), Redis/disk persistence.

</domain>

<decisions>
## Implementation Decisions

### Token Format (LOCKED)
- Format: `mcp4.v1.<base64url(12-byte-nonce + AES-256-GCM-ciphertext + 16-byte-tag)>`
- Encryption: AES-256-GCM, 12-byte random nonce per token, 16-byte auth tag
- AAD: `Buffer.from(profile_id, 'utf8')` — binds token to profile, prevents cross-profile replay
- Payload fields (short names to minimize token size):
  - `v: 1` — version
  - `at: string` — IdP access_token (REQUIRED)
  - `rt?: string` — IdP refresh_token
  - `exp?: number` — access token expiry as ms-since-epoch
  - `cid?: string` — OAuth client_id
  - `sc?: string[]` — scopes
  - `pid: string` — profile_id (REQUIRED, also used as AAD)
  - `iat: number` — envelope issued-at ms-since-epoch
  - `creg?: { id, ru?, gt?, rt_?, sc? }` — client registration snapshot (see below)
- `client_secret` is NEVER embedded — DCR clients are public PKCE clients without one

### Token Prefix (LOCKED)
- Magic prefix `mcp4.v1.` enables fast O(1) format detection without attempting decryption
- `isEncryptedToken(token): boolean` — `token.startsWith('mcp4.v1.')`
- The prefix + base64url chars pass the existing `validateToken` regex `^[A-Za-z0-9._~+/:=-]+$`

### Key Derivation (LOCKED)
- Env var: `MCP4_OAUTH_KEY`
- `deriveTokenKey(raw: string): Buffer`:
  - If `raw` is exactly 64 hex chars → `Buffer.from(raw, 'hex')` (32 bytes exactly)
  - Otherwise → `SHA-256(raw)` → 32 bytes (accepts any passphrase)
- If `MCP4_OAUTH_KEY` not set → log warn at startup, operate in plain-token mode (backward compat)

### Client Registration Embedding (LOCKED)
- `creg` embeds the OAuth client registration snapshot so on restart the client does not need
  to re-register. The AES-GCM auth tag IS the signature — successful decryption proves gateway
  created this registration, no separate HMAC needed.
- `creg` fields (short names): `id` (client_id), `ru` (redirect_uris), `gt` (grant_types),
  `rt_` (response_types), `sc` (scope string)
- `client_secret` NEVER embedded — field intentionally absent even if client has one
- On session init from envelope: call `oauthProvider.clientsStore.registerClient(creg)` to
  re-populate in-memory client store without requiring client to re-register

### DEFAULT_MAX_TOKEN_LENGTH Change (LOCKED)
- Raise `DEFAULT_MAX_TOKEN_LENGTH` constant from 1000 to 4096 in `http-transport.ts`
- Measured token sizes with creg: short opaque ~640 chars, medium JWT ~1084, large JWT ~1578
- MCP SDK client and RFC 6750 impose no token length limits — only our own constant is the bottleneck
- `validateToken()` body unchanged; env var `MCP4_TOKEN_MAX_LENGTH` still overrides

### storeOAuthTokens() Return Type Change (LOCKED)
- Change `private storeOAuthTokens(): void` → `private storeOAuthTokens(): string`
- Returns the token to give to client (encrypted envelope or plain access_token)
- Add optional 5th parameter: `registeredClient?: OAuthClientInformationFull`
- Both in-memory Maps use the returned token as key (not the raw IdP access_token)
- On encryption failure → warn, fall back to plain access_token (no crash)

### Call Sites for storeOAuthTokens() (LOCKED)
- Line ~1948 (auth_code grant): fetch `registeredClient` before calling, wrap response in
  envelope: `{ ...tokens, access_token: clientToken }` if encrypted
- Line ~1971 (refresh_token grant): same pattern
- Line ~4249 (internal refreshAccessToken): no `registeredClient` — assign `session.authToken = newClientToken`
  and remove the now-redundant direct `session.authToken = tokens.access_token` assignment

### Session Init Fallback Path (LOCKED)
- After both Map lookups fail AND `isEncryptedToken(token)` is true AND `tokenKey` is set:
  - Call `decryptTokenPayload(token, this.config.tokenKey, profileState.profileId)`
  - On success: populate `refreshToken`, `accessTokenExpiresAt`, `scopes`, `oauthClientId` from envelope
  - If `envelope.creg` present: call `oauthProvider.clientsStore.registerClient(...)` to restore client
  - Log `info` with `restoredClientReg` flag
  - On failure (null): log `debug`, session continues without OAuth metadata (behaves as plain bearer)
- `session.authToken` = encrypted envelope (set by unchanged `createSession()` call)
- `session.refreshToken` = raw IdP `rt` from envelope (used by `refreshAccessToken()` as-is)

### Startup Warning (LOCKED)
- In `HttpTransport` constructor, after `this.config = Object.freeze(...)`:
  - If `!this.config.tokenKey` → `this.logger.warn('MCP4_OAUTH_KEY not set...')`

### What NOT to Change (LOCKED)
- `refreshAccessToken()` internal logic — operates on `session.refreshToken` (raw IdP rt), unchanged
- `InboundAuthTokenStore` — no structural changes, remains a warm-cache layer
- `extractAuthToken()` — no changes, regex already accepts the token format
- `SessionData` interface — no new fields needed
- Enterprise JWT grant path — uses `inboundAuthTokenStore.issue()`, unaffected

### Known Limitation (document in module header)
- If IdP uses rotating refresh tokens AND server restarts after ≥1 in-session token refresh,
  the client holds old envelope with stale `rt` → re-auth needed (same as today)
- For non-rotating refresh tokens: zero-reauth across arbitrary restarts

### Phase 5 Extensibility (LOCKED)
- `TokenEnvelopePayload` interface must support future fields `upstreamAt?` and `upstreamRt?`
  (reserved for Phase 5 outbound OAuth proxy) — do NOT add them now, just keep interface open

</decisions>

<specifics>
## Specific Ideas

### New File: src/auth/token-envelope.ts
Pure crypto module, zero side effects, no deps beyond `node:crypto`.

```typescript
// Exported interface
export interface TokenEnvelopePayload {
  v: 1;
  at: string;        // IdP access_token
  rt?: string;       // IdP refresh_token
  exp?: number;      // access token expiry (ms epoch)
  cid?: string;      // OAuth client_id
  sc?: string[];     // scopes
  pid: string;       // profile_id (AAD binding)
  iat: number;       // issued-at (ms epoch)
  creg?: {
    id: string;      // client_id
    ru?: string[];   // redirect_uris
    gt?: string[];   // grant_types
    rt_?: string[];  // response_types
    sc?: string;     // scope string
  };
}

// deriveTokenKey: 64-char hex → 32-byte Buffer; else SHA-256(raw)
// isEncryptedToken: token.startsWith('mcp4.v1.')
// encryptTokenPayload: randomBytes(12) nonce + AES-256-GCM + setAAD(pid) → 'mcp4.v1.' + base64url
// decryptTokenPayload: NEVER throws; null on any failure; validates v===1, at type, pid match
```

### Test File: src/auth/token-envelope.test.ts (17 test cases)
1. deriveTokenKey — 64-char hex → 32-byte Buffer
2. deriveTokenKey — arbitrary string → 32-byte via SHA-256
3. isEncryptedToken — true/false cases incl. mcp4.v2.* → false
4. Round-trip full payload
5. Round-trip minimal payload (no rt/exp/cid/sc)
6. Wrong key → null (no throw)
7. Tampered ciphertext byte → null
8. Tampered auth tag byte → null
9. Cross-profile replay (pid mismatch) → null
10. Plain token (no prefix) → null fast-path
11. Truncated token (< 28 bytes after prefix) → null
12. Invalid base64 suffix → null
13. Same payload → two different tokens (nonce randomness)
14. Output passes validateToken regex `^[A-Za-z0-9._~+/:=-]+$`
15. null/undefined/garbage → null, never throw
16. Round-trip with creg → all subfields preserved
17. Round-trip without creg → envelope.creg is undefined

### Token Size Reference (from measurement)
```
Short opaque IdP token (~36 chars at + ~30 chars rt + creg): ~638-644 chars
Medium JWT (~400 chars at): ~1084 chars
Large JWT (~800 chars at): ~1578 chars
```
All fit within new DEFAULT_MAX_TOKEN_LENGTH = 4096.

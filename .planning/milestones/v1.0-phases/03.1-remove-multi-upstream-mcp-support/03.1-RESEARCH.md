## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01 — `upstream_mcp_from_env` JSON format:**
After the type change, `upstream_mcp_from_env` must contain a single JSON **object**
(`{name: ..., transport: ...}`), not an array. An array value produces a `ValidationError`
with a clear migration message: "upstream_mcp_from_env must contain a single JSON object,
not an array. Change [...] to {...}". `parseUpstreamMcpJson` becomes a simple
`JSON.parse` + Zod schema validation with no array-handling branch.

**D-02 — `name` field:**
The `name` field is **kept** on `UpstreamMcpServerConfig`. It is still useful for
structured log fields, error messages, and the connection manager dedup key. No type change
needed on `UpstreamMcpServerConfig` itself beyond removing it from an array context.

**D-03 — Profile config migration (breaking change):**
Existing YAML/JSON profiles using array syntax (`upstream_mcp: [{...}]`) receive a
hard `ValidationError` after the schema change: "upstream_mcp must be a single object, not
an array. Change `upstream_mcp: [{...}]` to `upstream_mcp: {...}`". No silent coercion.
The error must fire at profile load time (schema validation catches it before D-02/D-03
runtime checks).

**D-04 — Connection manager key scheme:**
The `UpstreamConnectionManager` dedup key stays `${sessionId}:${provider.name}`.
No changes to connection manager internals. The `name` field on the single config satisfies
the key requirement at zero additional cost.

**D-05 — Downstream call site cleanup:**
All `?.length &&` guards on `upstreamMcp` change to direct presence checks
(`upstreamMcp &&`). All `[0]` index accesses change to direct property access.
The single `for...of` loop in `http-transport.ts:2865` changes to a direct call using
the singular config value.

**D-06 — Schema regeneration:**
After changing `upstream_mcp` in `src/types/profile.ts` from
`UpstreamMcpServerConfig[]` to `UpstreamMcpServerConfig`, run `npm run generate-schemas`.
The `generated-schemas.ts` field changes from `z.array(upstreamMcpServerConfigSchema)` to
`upstreamMcpServerConfigSchema`. Do NOT manually edit `generated-schemas.ts`.

**D-07 — Profile-loader D-03 check removal:**
The existing D-03 runtime check in `profile-loader.ts` (rejects `> 1 providers`) is
removed. The Zod schema change makes it impossible to even parse an array value as a
valid config, so the runtime check becomes dead code. D-02 check (`?.length &&`) also
simplifies to a direct presence check.

### Claude's Discretion

- Test helper function `makeProfile(upstream_mcp: unknown[])` in upstream-mcp-config.test.ts —
  update signature to accept singular object; update all test fixtures accordingly.
- `upstream_mcp_from_env` test cases that pass array JSON — update to pass object JSON and
  add one negative test confirming array input errors.

## Summary

This phase is a **purely internal type-narrowing refactor**: change `Profile.upstream_mcp`
from `UpstreamMcpServerConfig[]` to `UpstreamMcpServerConfig` end-to-end. The runtime
single-provider constraint already exists in profile-loader (D-03 check at line 100); this
phase makes the type system enforce that constraint at compile time and at Zod parse time,
so the runtime check becomes redundant and is removed.

There is no external-library research needed — every change is local to the codebase. The
generated Zod schema (`src/generated-schemas.ts`) is regenerated automatically from
`src/types/profile.ts` via `npm run generate-schemas` (uses `ts-to-zod ^5.1.0`). The JSON
schema (`profile-schema.json`) is then synchronized via `scripts/sync-profile-schema.js`.

**Primary recommendation:** Make the type change in `src/types/profile.ts` first, run
`npm run generate-schemas`, verify the generated `upstream_mcp: upstreamMcpServerConfigSchema.optional()`
in `generated-schemas.ts`, then mechanically update the eight other source files and six
test files. Final step: add exactly two new negative tests (array YAML rejected; array env
JSON rejected) and delete the now-dead "rejects > 1 providers" test.

### Pattern 2: Lean ValidationError with descriptive `path`
**What:** All upstream-mcp validation errors use `new ValidationError(message, { path })`
where `path` is the dotted JSON Pointer-style location.
**Where established:** `src/profile/upstream-mcp-config.ts` lines 17-28, 80-94, 105-142,
167-218; pervasively used elsewhere.
**Style guide (verified by reading existing strings):**
- Lowercase first letter; no terminal period
- `path` mirrors the field location and gets a sub-segment for nested errors
- Example existing string: `"upstream_mcp_from_env must not be empty"`
- Example existing nested path: `path: "upstream_mcp[0].auth.header_name"`
- After this phase the index drops: `path: "upstream_mcp.auth.header_name"`

### Pattern 3: Resolver returns the validated, normalised config

shape. Loader assigns the result back to `profile.upstream_mcp` (line 87). After the
refactor this return type changes from `UpstreamMcpServerConfig[] | undefined` to

### Anti-Patterns to Avoid
- **Hand-editing `src/generated-schemas.ts`.** It will be overwritten by the next
  `npm run generate-schemas`. The check script `check-profile-schema-sync.js` exists
  precisely because this is a recurring trap. Edit the source TS file only.
- **Coercing array → object silently** in `parseUpstreamMcpJson` or in the loader. D-01 and
  D-03 require a hard `ValidationError` with a migration message. Silent coercion would
  hide misconfigured profiles.
- **Keeping the loader D-03 check "just in case".** D-07 explicitly retires it; once Zod
  rejects arrays at parse time, the runtime check is dead code that lies about why a config
  is rejected (the user sees the loader message, not the schema message). Delete it.
- **Treating the resolver's array dedup-by-name set as load-bearing.** It is currently
  there to detect duplicate provider names within an array. With singular config, two
  providers cannot exist simultaneously, so the dedup logic also goes. Removing it is the
  whole point.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TS interface → Zod schema sync | A second hand-written Zod schema | `npm run generate-schemas` (existing pipeline) | Drift detection already exists in `scripts/check-profile-schema-sync.js`; manual schemas always drift |
| Array → singular runtime coercion | A migration shim that wraps `[0]` reads | A hard `ValidationError` at schema parse time | Silent coercion hides misconfiguration. CONTEXT D-03 mandates explicit migration error |
| Detecting "array vs object" in upstream config | `Array.isArray` checks scattered through call sites | Zod schema rejection (single object only) | Zod is already the validation layer; adding parallel checks invites divergence |
| Connection dedup key | Synthetic ID for the singular provider | Keep `${sessionId}:${provider.name}` (D-04) | `name` is preserved per D-02; the existing key already works for one connection |

**Key insight:** The simplest possible refactor wins here. The runtime constraint already
exists; this phase just relocates it from the loader (procedural check) into the type
system (declarative — Zod + TS). Resist any urge to "improve" surrounding code while
visiting these sites; uncorrelated changes increase blast radius for no benefit.

## Common Pitfalls

### Pitfall 1: Forgetting to regenerate `profile-schema.json`
**What goes wrong:** IDEs (VSCode, JetBrains) read `profile-schema.json` for autocomplete
and inline validation. If you only regenerate `generated-schemas.ts` (Zod) and skip the JSON
schema sync, IDEs still suggest array syntax to users authoring profiles.
**Why it happens:** Two outputs, two scripts. `npm run generate-schemas` calls both, but a
manual `npx ts-to-zod ...` run skips the second step.
**How to avoid:** Always run `npm run generate-schemas` (the npm script), not a raw
`ts-to-zod` invocation. Verify both `src/generated-schemas.ts` AND `profile-schema.json`
appear in `git status` after the regeneration step.
**Warning signs:** `scripts/check-profile-schema-sync.js` (run by `npm run check-schema-sync`)
exits non-zero in CI; or IDEs autocomplete `[]` for the field while runtime rejects arrays.

### Pitfall 2: Touching `validateUpstreamProvider`'s return path without updating tests
**What goes wrong:** The error path-string changes from `upstream_mcp[0].auth.header_name`
to `upstream_mcp.auth.header_name`. Tests in `profile-loader.test.ts` (e.g. line 2909) match
the exact substring. Forgetting to update them produces failing tests with a confusing
"expected substring not found" message that obscures the type-narrow refactor.
**How to avoid:** After running tests, scan failure messages for `upstream_mcp[0]` and
update each match in test expectations. There are ~5-8 such test assertions; do them all
together in one pass through the test files.
**Warning signs:** Test failures whose assertion string includes `[0]` after the refactor.

### Pitfall 3: Leaving `Array.isArray` checks in non-loader code
**What goes wrong:** Two non-loader sites (`profile-resolver.ts` line 187 and
`generic-profile.test.ts` line 245) inspect raw profile JSON BEFORE Zod validates it. They
must continue to handle the case where a user-authored file has the old shape, but their
purpose changes from "iterate the array" to "detect & flag legacy shape" or "treat singleton
object as the new shape".
**Why it happens:** These sites read profile JSON as `unknown` for env-var collection / list
view rendering, intentionally avoiding Zod parse. They survive the type narrow without
errors but produce wrong results (e.g., `hasUpstreamMcp = false` for a legacy array, when
in reality it should still flag for migration).
**How to avoid:** Read these two sites carefully and rewrite the predicate to match the new
intent: "is this a non-array, non-null object?" If you want to keep the legacy-array UX in
list view (so users still see "uses upstream MCP" before they're forced to migrate),
preserve `Array.isArray(...) && length > 0` as a side branch. Otherwise, narrow.
**Warning signs:** A pre-migration profile JSON with `upstream_mcp: [{...}]` no longer shows
"upstream MCP" in profile listings, leaving operators puzzled. Decide explicitly.

### Pitfall 4: The `profile-resolver.test.ts` "multiple entries" test
**What goes wrong:** Test at line 100 specifically constructs `upstream_mcp` with two
entries to assert env-var collection from BOTH. With single-config, the test scenario
becomes impossible.
**How to avoid:** Rewrite the test as either (a) "rejects multi-entry upstream_mcp at
schema parse time" (delete env-collection coverage of this scenario; it's redundant since
single-entry already exercises the same code path), or (b) split into two profiles — but
the latter doubles fixture noise for no extra coverage.
**Warning signs:** TypeScript error on the test fixture itself once the type narrows.

### Pitfall 5: Connection manager assumptions
**What goes wrong:** `UpstreamConnectionManager` keys connections by
`${sessionId}:${providerName}`. The map key was designed for "many connections per session"
(line 60 comment) — line 80 already notes the "single-provider-per-profile assumption for
phase 2". With the type narrow, that comment becomes load-bearing fact rather than an
incidental assumption.
**How to avoid:** Per D-04, the connection manager itself does not change. But update the
line 60 inner-map comment to reflect that the inner map is now a degenerate
single-entry-max map (or note this in a follow-up). For Phase 03.1 specifically: leave it
alone — D-04 says no logic change.
**Warning signs:** A future contributor reads "Outer key: sessionId, inner key: providerName"
and proposes adding multi-provider support back, not realising the type system now forbids it.

## Code Examples

### Singular `parseUpstreamMcpJson` (after refactor)
```typescript
// src/profile/upstream-mcp-config.ts (D-01 — array input is now a hard error)
function parseUpstreamMcpJson(rawValue: string, path: string): UpstreamMcpServerConfig {
  let parsed: unknown;
  try {
    parsed = JSON.parse(rawValue);
  } catch {
    throw new ValidationError(`${path} must contain valid JSON`, { path });
  }

  if (Array.isArray(parsed)) {
    throw new ValidationError(
      `${path} must contain a single JSON object, not an array. ` +
      `Change [{...}] to {...}`,
      { path },
    );
  }
  if (parsed === null || typeof parsed !== 'object') {
    throw new ValidationError(`${path} must contain a JSON object`, { path });
  }

  const result = upstreamMcpServerConfigSchema.safeParse(parsed);
  if (!result.success) {
    const issue = result.error.issues[0];
    const fieldPath = issue?.path.length ? `${path}.${issue.path.join('.')}` : path;
    throw new ValidationError(
      `${fieldPath}: ${issue?.message ?? 'invalid upstream MCP provider'}`,
      { path: fieldPath },
    );
  }
  return result.data;
}
```

## Open Questions

1. **Should `profile-resolver.ts:449` (`hasUpstreamMcp`) keep array tolerance for legacy profiles in list view?**
   - What we know: This is read-only profile listing logic operating on raw JSON before Zod
     validation. Legacy `upstream_mcp: [{...}]` profiles still exist on users' disks until
     they migrate.
   - What's unclear: Does the project want list view to flag these as "uses upstream MCP"
     (helpful UX) or refuse to recognise them (forcing migration immediately)?
   - Recommendation: Keep array tolerance in list view (`Array.isArray(...) && .length > 0`
     as an OR branch), so `gsd:list-profiles`-style commands still surface upstream-MCP-in-use
     status until the user opens the profile and gets the proper migration error. Document
     the choice in a code comment.

2. **`profile-resolver.test.ts` "multiple entries" coverage — preserve or drop?**
   - What we know: Two tests (lines 100, 108) exercise env-var collection across multiple
     auth-bearing entries. Single-entry already covers the auth-iteration code path.
   - What's unclear: Was the multi-entry case ever a real defect-discovery test, or
     incidental?
   - Recommendation: Drop the "multiple entries" expectation; replace with a "rejects array"
     schema-level negative test mirroring D-03. No coverage loss.

3. **Should `mcp-server.ts:734` and `:1408` be unified into a single accessor?**
   - What we know: Both pass `upstreamMcp` into `HttpTransportConfig` / `HttpProfileContext`
     contexts. The two sites use different sources (`this.profile.upstream_mcp` vs
     `profileContext.upstreamMcp`).
   - What's unclear: Whether a single accessor is worth introducing in this phase.
   - Recommendation: **Out of scope.** Phase 03.1 is a type-narrow refactor; do not
     refactor data flow. Leave the two sites as-is with their types narrowed. Worth a
     follow-up issue if it ever becomes painful.

# Phase 03.2: Profile env-var description field - Context

**Gathered:** 2026-05-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Add a mechanism for server admins to attach per-profile HTML descriptions to profiles displayed on the HTML index page. Descriptions are injected via the `MCP4_PROFILES_DESCRIPTION` environment variable (not embedded in profile JSON files). The description renders in the profile detail view, in the Profile card, immediately before the profile's own `description` field.

Use case: admins can document how to obtain credentials, link to internal wikis, or add any guidance relevant to a profile — without modifying profile JSON.

</domain>

<decisions>
## Implementation Decisions

### Schema — env var format

- **D-01:** Mechanism is a new env var `MCP4_PROFILES_DESCRIPTION` parsed at server startup.
- **D-02:** Value is a JSON object. Keys are profile identifiers (profile-id, profile-name, or profile-alias — any of these). Values are description strings.
  - Example: `MCP4_PROFILES_DESCRIPTION={"gitlab":"Get your <a href='...'>token</a> here","github":"Bearer token required"}`
- **D-03:** One description per profile — a single HTML/text blob, not a per-env-var-name map.

### Key resolution

- **D-04:** Any key in the JSON may be a profile-id, profile-name, or profile-alias. Resolution checks all three for each profile.
- **D-05:** If two or more keys in the JSON resolve to the same profile (e.g. both "gitlab" and an alias "gl" are present and both match the same profile), it is a configuration error: **fail fast at startup** — log the conflict and refuse to start.

### HTML content

- **D-06:** Description values are rendered as **raw HTML** in the browser. No sanitization. Admin controls server env vars — trust level equivalent to profile config file access. Links (`<a>`), bold (`<strong>`), paragraphs etc. work as-is.

### Invalid / missing env var

- **D-07:** If `MCP4_PROFILES_DESCRIPTION` is set but contains invalid JSON → **fail fast at startup** (consistent with existing pattern: `key_from_env` typo → server refuses to start).
- **D-08:** If `MCP4_PROFILES_DESCRIPTION` is not set → no extra descriptions; all profiles render normally.
- **D-09:** If a profile has no matching key in the JSON map → no extra description; render is unchanged.

### Render placement

- **D-10:** Renders in the **detail view only** — when the user clicks a profile in the sidebar, the Profile card in the detail pane shows the extra description **before** `profile.description`.
- **D-11:** The sidebar list item (subtitle line) is **unchanged** — it still shows `profile.description` only.
- **D-12:** Extra description is injected as raw HTML (not escaped). `profile.description` continues to be HTML-escaped as today.

### Claude's Discretion

- Exact field name on the enriched profile object passed to the HTML template (e.g., `extraDescription`, `adminDescription`, or similar) — Claude picks.
- Whether `MCP4_PROFILES_DESCRIPTION` validation/parsing lives in `src/core/index.ts`, a new `src/profile/profile-description-env.ts`, or inline in `buildProfileIndexPayload` — Claude picks following existing conventions.
- Whether the conflict-detection error is a `ValidationError` or a new `ConfigurationError` — Claude picks the closest existing typed error.

</decisions>

<specifics>
## Specific Ideas

- Env var name is exactly `MCP4_PROFILES_DESCRIPTION` (follows existing `MCP4_*` namespace)
- JSON value example: `{"gitlab":"Get your token at <a href='https://gitlab.example.com/-/user_settings/personal_access_tokens'>Personal Access Tokens</a>","github":"M2M clients: use a PAT with <code>repo</code> scope"}`
- Keys can be profile-id, profile-name, or profile-alias — any match activates the description for that profile
- Conflict detection should name both conflicting keys and the matched profile in the error message

</specifics>

Define the foundational types, typed errors, credential store, credential extraction from HTTP headers, and redaction extensions for upstream MCP connections.

Purpose: All subsequent upstream modules (connection manager, heartbeat) depend on these types and error classes. Credential redaction must be in place before any credential handling code exists, establishing the security boundary first. Credential extraction resolves RESEARCH.md Open Question #1 by using the X-Upstream-Authorization HTTP header.

Output: Type definitions, 4 error classes, credential store with header builder, credential extractor for session init, extended redaction infrastructure, and comprehensive tests for all.

  <action>
    Decision (resolves RESEARCH.md Open Question #1): Use HTTP header `X-Upstream-Authorization` for credential delivery. This keeps credential delivery at the transport layer, consistent with existing auth header patterns. MCP init params are protocol-level and modifying them would be non-standard.

    Header format: `X-Upstream-Authorization: provider-name=token-value[,provider-name2=token-value2]`
    - Comma-separated entries for multiple providers
    - Each entry is `providerName=tokenValue` (split on first `=` only to handle base64 tokens)
    - Provider names must match `upstream_mcp[].name` in the profile

    1. Write tests FIRST in `src/upstream/upstream-credential-extractor.test.ts`:
       - Test single provider extraction: header with one entry returns correct Map
       - Test multiple providers: comma-separated entries return Map with all entries
       - Test missing header: returns undefined
       - Test empty header: returns undefined
       - Test unknown provider (not in profile config): entry ignored, not in result Map
       - Test token with `=` chars (base64): only splits on first `=`
       - Test whitespace handling: trims provider names and tokens
       - Test UPSTREAM_AUTH_HEADER constant value

    2. Create `src/upstream/upstream-credential-extractor.ts`:
       - Export `const UPSTREAM_AUTH_HEADER = 'x-upstream-authorization'` (lowercase for Express req.headers)
       - Export `function extractUpstreamCredentials(headers: Record<string, string | string[] | undefined>, allowedProviders: string[]): Map<string, string> | undefined`
         - Read `headers[UPSTREAM_AUTH_HEADER]`
         - If missing or empty, return undefined
         - Split value by `,` to get entries
         - For each entry, split on first `=` to get `[providerName, token]`
         - Trim whitespace on both parts
         - Only include if providerName is in allowedProviders set
         - Return Map of providerName -> token, or undefined if no valid entries
         - NEVER log token values. Log at debug level: "Extracted upstream credentials for N providers" with provider names only (no tokens)

    Note: This task creates the extraction function. The wiring into http-transport.ts createSession() is a separate concern for Phase 2 integration, but the function signature is designed so that the caller in http-transport.ts can do:
    ```typescript
    const upstreamCreds = extractUpstreamCredentials(req.headers, profileState.upstreamProviderNames);
    // pass upstreamCreds to createSession -> stored in SessionData.upstreamCredentials
    ```

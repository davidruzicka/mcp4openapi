## Schema Design

| Option | Description | Selected |
|--------|-------------|----------|
| Field in profile JSON | Add `env_var_descriptions: { VAR_NAME: { description } }` to profile files | |
| `MCP4_PROFILES_DESCRIPTION` env var | JSON map of profile-identifier → description blob, injected at startup | ✓ |
| Inline on interceptor config | Add `description` to `auth.value_from_env` etc. | |

**User's choice:** `MCP4_PROFILES_DESCRIPTION` env var containing JSON `{"<profile-id|name|alias>":"<description>,...}`
**Notes:** User specifically proposed this approach in their first answer. Admin sets this once per deployment without touching profile JSON files. HTML content explicitly mentioned as desirable (for links, formatting).

---

## Scope

| Option | Description | Selected |
|--------|-------------|----------|
| Per-profile (one blob) | One description per profile identifier, shown on the HTML index | ✓ |
| Per-env-var within profile | `{"profile-id":{"VAR_NAME":"description",...}}` — each env var gets its own description | |

**User's choice:** Per-profile — one HTML blob per profile
**Notes:** "Yes — one description per profile" confirmed.

---

## HTML Policy

| Option | Description | Selected |
|--------|-------------|----------|
| Raw HTML — admin-trusted | Content injected directly, links and formatting work | ✓ |
| Sanitized HTML | Strip dangerous tags (would require DOMPurify or custom allowlist) | |

**User's choice:** Raw HTML — admin-trusted
**Notes:** Admin controls server env vars; trust is equivalent to config file access.

## Key Conflict

| Option | Description | Selected |
|--------|-------------|----------|
| First match wins (id > name > alias) | Priority order resolution | |
| Last match wins | Simple iteration | |
| Conflict = error at startup | Multiple keys resolving to same profile → fail fast | ✓ |

**User's choice:** Conflict = error at startup
**Notes:** Log the conflict, name both keys and the matched profile, refuse to start.

## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Mechanism is a new env var `MCP4_PROFILES_DESCRIPTION` parsed at server startup.
- **D-02:** Value is a JSON object. Keys are profile identifiers (profile-id, profile-name, or profile-alias — any of these). Values are description strings.
  - Example: `MCP4_PROFILES_DESCRIPTION={"gitlab":"Get your <a href='...'>token</a> here","github":"Bearer token required"}`
- **D-03:** One description per profile — a single HTML/text blob, not a per-env-var-name map.
- **D-04:** Any key in the JSON may be a profile-id, profile-name, or profile-alias. Resolution checks all three for each profile.
- **D-05:** If two or more keys in the JSON resolve to the same profile (e.g. both "gitlab" and an alias "gl" are present and both match the same profile), it is a configuration error: **fail fast at startup** — log the conflict and refuse to start.
- **D-06:** Description values are rendered as **raw HTML** in the browser. No sanitization. Admin controls server env vars — trust level equivalent to profile config file access. Links (`<a>`), bold (`<strong>`), paragraphs etc. work as-is.
- **D-07:** If `MCP4_PROFILES_DESCRIPTION` is set but contains invalid JSON → **fail fast at startup** (consistent with existing pattern: `key_from_env` typo → server refuses to start).
- **D-08:** If `MCP4_PROFILES_DESCRIPTION` is not set → no extra descriptions; all profiles render normally.
- **D-09:** If a profile has no matching key in the JSON map → no extra description; render is unchanged.
- **D-10:** Renders in the **detail view only** — when the user clicks a profile in the sidebar, the Profile card in the detail pane shows the extra description **before** `profile.description`.
- **D-11:** The sidebar list item (subtitle line) is **unchanged** — it still shows `profile.description` only.
- **D-12:** Extra description is injected as raw HTML (not escaped). `profile.description` continues to be HTML-escaped as today.

## Summary

Phase 03.2 introduces a single new server-wide env var `MCP4_PROFILES_DESCRIPTION` whose value is a JSON map from profile identifier (id / name / alias) → HTML description string. The map is parsed once at startup, fail-fast on JSON-parse failure or duplicate-resolution conflict. At HTML index render time, `buildProfileIndexPayload` enriches each `ProfileIndexSourceProfile` with a new optional field (working name `adminDescription`) when its id/name/alias matches a key in the parsed map. The HTML template's `renderDetail` function (around line 1874–1968 of `html/profile-index.html`) injects that field as raw HTML directly **before** the existing escaped `profile.description` line. Sidebar (`renderList`, line 2462) is unchanged.

The work is small, well-bounded, and touches three layers: (1) startup env-var parse + conflict check, (2) profile-index payload enrichment, (3) HTML detail-view template patch + accompanying tests. There are no external dependencies — only `process.env`, existing typed errors, existing template helpers, existing test framework.

**Primary recommendation:** Implement startup parsing in a new module `src/profile/profile-description-env.ts` that exports a pure function `parseProfilesDescriptionEnv(rawJson: string | undefined): Map<string, string> | undefined` plus a `resolveProfileAdminDescription(profile: ListedProfileDetails, map: Map<string, string>): string | undefined` helper. Wire the parse call in `src/core/index.ts` startup (alongside the other `MCP4_*` reads), and pass the resulting map down to the HTTP transport so `buildProfileIndexPayload` can enrich. Use `ConfigurationError` for both invalid-JSON and duplicate-resolution failures (matches existing `Profile is missing openapi_spec_path` and `Profile ID or alias is not unique` patterns in `profile-resolver.ts` lines 432, 577).

### Pattern A: Startup env-var parse + fail-fast (recommended placement)

**What:** Parse `MCP4_PROFILES_DESCRIPTION` once during `main()` in `src/core/index.ts`, store the resulting `Map<string, string> | undefined`, and pass it through to the HTTP transport (it is the only consumer for the HTML index path).

**When to use:** Always — this is the only correct placement given D-07 (invalid JSON must fail at startup, not at first request).

**Example:**
```typescript
// src/profile/profile-description-env.ts (NEW)
import { ConfigurationError } from '../core/errors.js';

/**
 * Parse MCP4_PROFILES_DESCRIPTION env var into a key → description map.
 *
 * Returns undefined when the env var is unset (D-08).
 * Throws ConfigurationError on invalid JSON (D-07) or non-object payload.
 *
 * Conflict detection (D-05) is NOT done here — keys may legitimately overlap
 * with profile aliases on different profiles. It happens in resolveProfileAdminDescriptions
 * once profiles have been loaded.
 */
export function parseProfilesDescriptionEnv(raw: string | undefined): Map<string, string> | undefined {
  if (!raw || raw.trim().length === 0) return undefined;

  let parsed: unknown;
  try {
    parsed = JSON.parse(raw);
  } catch (error) {
    throw new ConfigurationError('MCP4_PROFILES_DESCRIPTION is not valid JSON', {
      envVar: 'MCP4_PROFILES_DESCRIPTION',
      error: error instanceof Error ? error.message : String(error),
    });
  }

  if (!parsed || typeof parsed !== 'object' || Array.isArray(parsed)) {
    throw new ConfigurationError('MCP4_PROFILES_DESCRIPTION must be a JSON object', {
      envVar: 'MCP4_PROFILES_DESCRIPTION',
      receivedType: Array.isArray(parsed) ? 'array' : typeof parsed,
    });
  }

  const map = new Map<string, string>();
  for (const [key, value] of Object.entries(parsed as Record<string, unknown>)) {
    if (typeof value !== 'string') {
      throw new ConfigurationError('MCP4_PROFILES_DESCRIPTION values must be strings', {
        envVar: 'MCP4_PROFILES_DESCRIPTION',
        key,
        receivedType: typeof value,
      });
    }
    map.set(key, value);
  }
  return map;
}
```

### Pattern B: Resolve descriptions per profile + conflict detection

**What:** Given the parsed map and the list of profiles (`ListedProfileDetails[]`), produce a `Map<profileId, description>` and throw on duplicate resolution (D-05).

**When to use:** Once at startup, after `listProfilesDetailed()` returns. Result is then plumbed into the HTTP transport (single source of truth — no per-request reparse).

**Example:**
```typescript
// src/profile/profile-description-env.ts (NEW, continued)
import { ConfigurationError } from '../core/errors.js';
import type { ListedProfileDetails } from './profile-resolver.js';

/**
 * Resolve description-map keys against profiles.
 *
 * Each profile is matched by profile_id, profile_name, or any alias (D-04).
 * Multiple keys resolving to the same profile is a ConfigurationError (D-05).
 * Keys that match no profile are silently ignored — admin may have stale entries
 * for retired profiles, that's not a hard failure.
 *
 * Returns Map<profileId, description>. Empty map when descriptions undefined.
 */
export function resolveProfileAdminDescriptions(
  descriptions: Map<string, string> | undefined,
  profiles: ListedProfileDetails[],
): Map<string, string> {
  const result = new Map<string, string>();
  if (!descriptions || descriptions.size === 0) return result;

  // For each (key, description), find profiles it matches. If 2+ matching keys
  // resolve to the same profile, that's a conflict.
  // Track first key per profile so we can include it in the conflict error.
  const firstKeyByProfile = new Map<string, string>(); // profileId -> first key that matched

  for (const [key, description] of descriptions.entries()) {
    for (const profile of profiles) {
      const matches =
        profile.profileId === key ||
        profile.profileName === key ||
        profile.profileAliases.includes(key);
      if (!matches) continue;

      const existingKey = firstKeyByProfile.get(profile.profileId);
      if (existingKey && existingKey !== key) {
        throw new ConfigurationError(
          'MCP4_PROFILES_DESCRIPTION has multiple keys resolving to the same profile',
          {
            envVar: 'MCP4_PROFILES_DESCRIPTION',
            profileId: profile.profileId,
            profileName: profile.profileName,
            conflictingKeys: [existingKey, key].sort(),
          },
        );
      }
      firstKeyByProfile.set(profile.profileId, key);
      result.set(profile.profileId, description);
    }
  }
  return result;
}
```

### Anti-Patterns to Avoid

- **Calling `JSON.parse` on every HTTP request:** Parse once at startup, pass the resolved `Map<profileId, description>` down to the transport. Re-parsing on each request makes failures latent (the server starts, then the first user request 500s) — directly contradicts D-07.
- **Wrapping the description in `escapeHtml`:** Defeats the entire feature (D-06: links, bold, paragraphs must work). The escape happens implicitly through `safeJsonForHtml` only for the JSON-string-context, not for the rendered HTML — see Pitfall §3.
- **Sanitizing or filtering HTML:** D-06 says no sanitization. Adding sanitization later is additive; baking it in now adds dependencies (`dompurify`, `sanitize-html`) for no current requirement.
- **Storing the description on the `Profile` JSON schema:** Out of scope — D-01 says the env var is the mechanism. Do NOT touch `src/types/profile.ts` or regenerate `profile-schema.json`.
- **Plumbing the map through `ProfileRegistry`:** `ProfileRegistry` is the wrong layer — it serves the runtime tool/spec resolution path. The description map is purely an HTML-index concern. Pass it directly to the HTTP transport (or to whatever `profileIndexProvider` callback owns the index).

## Common Pitfalls

### Pitfall 1: Conflict detection executed BEFORE profiles are loaded
**What goes wrong:** A naïve implementation parses the env var into a map and immediately validates "no duplicate keys" — but JSON.parse already enforces that (duplicate JSON object keys are last-wins by spec, no error). The actual conflict per D-05 is duplicate **resolution to the same profile**, which is only knowable once the profile list has been loaded.
**Why it happens:** Misreading D-05 as "no duplicate keys in JSON" instead of "no two distinct keys resolving to the same profile".
**How to avoid:** Two-phase resolution: (1) `parseProfilesDescriptionEnv` validates JSON shape only, (2) `resolveProfileAdminDescriptions` does the conflict check after `listProfilesDetailed()` runs. The plan must order startup steps: parse env → load profiles → resolve descriptions → instantiate transport.
**Warning signs:** "Conflict not detected when both `gitlab` (id) and `gl` (alias) are in the JSON" passing in dev but failing in CI integration test.

### Pitfall 2: Forgetting that JSON.parse silently de-duplicates JSON keys
**What goes wrong:** `JSON.parse('{"a":"x","a":"y"}')` returns `{a: "y"}` — a literal duplicate key in the JSON source is collapsed by the parser. So if an admin writes `MCP4_PROFILES_DESCRIPTION='{"gitlab":"foo","gitlab":"bar"}'`, only `bar` survives. This is **not** what D-05 means by "conflict" — D-05 is about distinct keys resolving to the same profile (e.g. `"gitlab"` matching `profile_id=gitlab` and `"gl"` matching alias of the same profile).
**Why it happens:** Conflating JSON-spec duplicate-key behavior with semantic duplicate-resolution.
**How to avoid:** Don't try to detect literal JSON duplicate keys (impossible after `JSON.parse`). Detect only resolution-conflicts in `resolveProfileAdminDescriptions`. Document the silent-collapse behavior in a `// Why:` comment.
**Warning signs:** A test like "duplicate JSON keys throw" — that test is unwriteable; remove it. The test that matters is "id + alias both in map throw".

### Pitfall 3: HTML-escape happens in *two* places — easy to miss
**What goes wrong:** The profile data flows through TWO layers of HTML safety:
  1. **Server side:** `safeJsonForHtml(enriched)` (line 321 of `profile-index.ts`) escapes `</` to `</` so the JSON blob can be embedded in a `<script>` tag without breaking out. **This is JSON-string escape, not HTML escape** — `<a href=...>` survives unchanged inside a JSON string.
  2. **Client side:** Template client-side `escapeHtml(...)` (function at line 559) is wrapped around fields like `profile.description` (line 1967), `profile.profileName`, etc. **This is the HTML escape** that would defeat raw-HTML rendering.
The bug: a developer copies the existing `${escapeHtml(description)}` line and produces `${escapeHtml(profile.adminDescription)}` — which would re-escape the `<a>` and produce literal `&lt;a&gt;` text in the page (the opposite of D-06).
**Why it happens:** Pattern-match on the surrounding code without reading what `escapeHtml` does.
**How to avoid:** Use `${profile.adminDescription || ''}` directly with NO escape wrapper. Add a `<!-- raw HTML by design (D-06) -->` HTML comment at the injection site. The integration test should assert that `<a href` survives literal in the rendered HTML output.
**Warning signs:** Test failure "expected `<a href` but got `&lt;a href`".

### Pitfall 4: Sidebar accidentally affected
**What goes wrong:** A developer notices `renderList` (line 2462) also reads `profile.description` and "helpfully" adds `profile.adminDescription` to the sidebar subtitle too. D-11 explicitly forbids this.
**Why it happens:** Symmetry bias — if it's on the profile object, surely it should appear everywhere.
**How to avoid:** Make D-11 a positive test: render the index, find the sidebar `<div class="profile-subtitle">` for a profile that has an admin description, assert the admin description is **NOT** present in that node. Only the detail card should contain it.
**Warning signs:** Snapshot test of `renderList` output changes when admin descriptions are added.

### Pitfall 5: Map propagation ordering
**What goes wrong:** `MCP4_PROFILES_DESCRIPTION` is parsed at startup, but the `HttpTransport` constructor or `buildProfileIndexPayload` is called before the map is plumbed in. Result: descriptions silently never render.
**Why it happens:** The wiring crosses three files (`core/index.ts` → `http-transport.ts` → `profile-index.ts`); easy to add the parse but forget to thread the value through.
**How to avoid:** End-to-end test: `process.env.MCP4_PROFILES_DESCRIPTION = JSON.stringify({gitlab: "<b>x</b>"})`, run startup, hit the HTML index endpoint with `Accept: text/html`, grep the response for `<b>x</b>` literal. If it's missing, the wiring is broken.
**Warning signs:** Unit tests on `buildProfileIndexPayload` pass but no description appears in the actual served HTML.

### Pitfall 6: Empty string as description
**What goes wrong:** `MCP4_PROFILES_DESCRIPTION='{"gitlab":""}'` — what should happen? The current rendering uses `profile.adminDescription ? <render> : ''` so empty string falls through (no extra `<div>` rendered) which is sensible. But `parseProfilesDescriptionEnv` should still allow it (typeof `""` === 'string').
**Why it happens:** Guard logic differs at parse vs render — easy to make them inconsistent.
**How to avoid:** Allow empty strings at parse time, treat them as "no description shown" at render time using truthy check. Document as "empty string == suppress" in module JSDoc.
**Warning signs:** Test "empty-string description rejected at startup" — that's wrong, it should be accepted and treated as no-op.

## Open Questions

1. **CSS class for the new wrapper element**
   - What we know: Existing wrapper classes include `profile-subtitle`, `profile-title`, `detail-card`. Adding raw HTML directly in a `profile-subtitle` class would inherit subtle styling (smaller text, gray) which may or may not be desired.
   - What's unclear: Whether the admin description should look the same as `profile.description` (use `profile-subtitle`) or visually distinct (new class with its own CSS).
   - Recommendation: Start with `<div class="profile-subtitle profile-admin-description">` — inherits the existing subtitle styling so links are readable, and ships an additional class hook for future styling without committing to a new visual treatment in this phase. Adding CSS is trivially extendable; visual design is out of scope per CONTEXT.

2. **`profile_data` JSON size growth**
   - What we know: `safeJsonForHtml(enriched)` already serializes the entire profile catalog into the HTML page. Each admin description adds N bytes per profile.
   - What's unclear: Whether there's a practical cap on description length (e.g., 4 KB per profile × 50 profiles = 200 KB extra HTML).
   - Recommendation: Don't add a length cap in this phase. Document in module JSDoc that admin descriptions ride in the page payload and very long values increase HTML size. Defer cap to a follow-up phase if it becomes a problem.

3. **Localization of the admin description**
   - What we know: The HTML index supports `cs` / `en` locales for static strings via `buildProfileIndexI18n`. Admin descriptions are a single string per profile.
   - What's unclear: Should descriptions support per-locale variants (`{"gitlab": {"en": "...", "cs": "..."}}`)?
   - Recommendation: NO — D-03 explicitly says "one description per profile — a single HTML/text blob". Out of scope. If needed, admin can write bilingual HTML directly: `<p lang="en">...</p><p lang="cs">...</p>`.

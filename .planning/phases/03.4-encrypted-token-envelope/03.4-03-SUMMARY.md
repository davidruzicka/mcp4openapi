# Phase 03.4 Plan 03: Wire Encrypted Token Envelope into HttpTransport Summary

**HttpTransport now issues `mcp4.v1.*` envelopes from /oauth/token + internal refresh, restores OAuth sessions from envelopes presented after restart (rehydrating refresh token + DCR client registration via creg), rejects cross-profile replay, and preserves byte-identical plain-token behavior when MCP4_TOKEN_KEY is unset (with a startup warn).**

## Accomplishments

- Added `import { encryptTokenPayload, decryptTokenPayload, isEncryptedToken } from '../auth/token-envelope.js'` immediately below the oauth-provider import line, keeping module concerns separate.
- `DEFAULT_MAX_TOKEN_LENGTH` raised from `1000` to `4096`; both consumers (`validateToken` and the Authorization header length guard) reference the constant by name and required no further change.
- `HttpTransport` constructor now emits a one-shot `warn` containing 'MCP4_TOKEN_KEY not set' immediately after `this.logger = logger;` when `this.config.tokenKey` is undefined - producing exactly one warn line at startup so operators see the deferred-encryption notice without spamming logs.
- `storeOAuthTokens` refactored from `void` to returning `string`, gained an optional 5th parameter `registeredClient?: OAuthClientInformationFull` whose fields populate `envelope.creg` (id->client_id, ru->redirect_uris, gt->grant_types, rt_->response_types, sc->scope) when present. Both maps are now keyed by the RETURNED token (envelope when encrypted, raw access_token otherwise) so subsequent requests round-trip correctly.
- Encryption-failure path: `try/catch` around `encryptTokenPayload` logs `'Token envelope encryption failed - falling back to plain access_token'` (warn) and falls back to keying the maps by `tokens.access_token` - never crashes, biases availability over confidentiality on misconfiguration.
- All three call sites updated:
  - **Auth-code grant** (~line 1948 area): fetches `registeredClient` via `clientsStore.getClient(client.client_id)`, passes it as the 5th arg, and conditionally spreads `{...tokens, access_token: clientToken}` when an envelope was issued.
  - **Refresh-token grant** (~line 1971 area): same shape.
  - **Internal refreshAccessToken** (~line 4249 area): removed `session.authToken = tokens.access_token` (which caused envelope/raw mismatch on next request), now assigns `session.authToken = newClientToken` from the `storeOAuthTokens` return value. No `registeredClient` passed - the existing session already has the client registered.
- Session-init envelope-decrypt fallback inserted immediately after the existing `else if (!internalToken)` debug branch (still inside the outer `if (authInfo.token && (authInfo.type === 'oauth' || authInfo.type === 'bearer'))` block):
  - Triggered only when `!internalToken && !refreshToken && this.config.tokenKey && isEncryptedToken(authInfo.token)` - the `!refreshToken` guard is essential so the warm-cache map lookup wins on the no-restart path and the fallback runs at most once per session.
  - On successful decrypt: rehydrates `refreshToken/accessTokenExpiresAt/scopes/oauthClientId` from the envelope, re-registers the DCR client via `clientsStore.registerClient` when `envelope.creg` is present (with sensible defaults: `ru ?? []`, `gt ?? ['authorization_code','refresh_token']`, `rt_ ?? ['code']`, `sc ?? ''`), and emits an `info` log line `'Session restored from encrypted token envelope after restart'` with profileId/hasRefreshToken/hasExpiry/oauthClientId/restoredClientReg flags.
  - On decrypt failure (cross-profile, wrong key, tampered): emits a `debug` log line and the session continues as a plain bearer with no crash and no 401.

## Decisions Made

- **storeOAuthTokens key correctness.** The original implementation keyed both `oauthTokensByAccessToken` and `inboundAuthTokenStore` by `tokens.access_token`. With envelopes the client presents the `mcp4.v1.*` form on subsequent requests, so the warm-cache lookup would have always missed and forced the slow decrypt fallback every request. Both maps are now keyed by the RETURNED `clientToken` so the warm-cache path wins and the decrypt fallback only runs for restart recovery.
- **Internal refresh authToken swap.** The previous `session.authToken = tokens.access_token` assignment was unconditionally raw, which produced the same envelope/raw mismatch within an existing session immediately after a token refresh. The fix is mechanical: assign the storeOAuthTokens return value. Plain-token mode is unaffected (the return equals `tokens.access_token` exactly).
- **Encryption-failure availability bias.** A `try/catch` around `encryptTokenPayload` lets the gateway fall back to plain-token mode for that single request when `tokenKey` is malformed (wrong length, etc.), with a `warn` log to alert operators. Crashing here would block all OAuth grants on a config typo - availability bias is correct for this surface.
- **Session-init fallback placement and `!refreshToken` guard.** The fallback is inserted after the existing `else if (!internalToken)` debug branch but inside the same outer `if (authInfo.token && ...)` block, so the warm-cache path is preserved untouched. The `!refreshToken` guard ensures the fallback only runs when both Map lookups missed, never redundantly.
- **registerClient guard on `profileState.oauthProvider`.** Phase 03.3 graceful degradation can leave `oauthProvider` as `null` when OAuth config is non-operational. The guard means session metadata still rehydrates from a presented envelope even in degraded-OAuth mode (refresh token + scopes still available); only the DCR re-registration is skipped, matching the broader graceful-degradation contract.
- **registerClient defaults.** The SDK's `redirect_uris` field is `z.ZodArray<z.ZodURL>` (required, non-empty in some shapes); `?? []` keeps the fallback safe and `?? ['authorization_code', 'refresh_token']`/`?? ['code']`/`?? ''` mirror the standard DCR public-PKCE-client shape so partial envelopes don't break registration.
- **Map keying by `clientToken` is the correct backward-compat point.** When `tokenKey` is unset, `clientToken === tokens.access_token` exactly, so the keys are byte-identical to pre-phase. Plain-token tests need no change to keep working - and indeed the existing `storeOAuthTokens` tests at lines 3800-3846 still pass unchanged.
- **DNS-rebinding test narrowing.** The pre-existing `'should allow loopback IP Host header with port and retain logging'` test asserted `testLogger.warn` was NEVER called. The new constructor warn for missing `MCP4_TOKEN_KEY` makes this assertion fail. Narrowed to `dnsRelatedWarns.toHaveLength(0)` (filters out the startup warn) so the original DNS-rebinding intent is preserved without false-positive on the new startup warn. Documented in deviation Rule 3.

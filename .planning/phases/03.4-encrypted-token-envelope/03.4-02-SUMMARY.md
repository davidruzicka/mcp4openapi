**HttpTransportConfig grows an optional `tokenKey?: Buffer` populated from `MCP4_TOKEN_KEY` via `deriveTokenKey()`, with whitespace trimmed for k8s ConfigMap tolerance and full backward compatibility when the env var is absent.**

- `HttpTransportConfig` exposes `tokenKey?: Buffer` immediately after `maxTokenLength`, with a JSDoc block that documents the dual-mode derivation (64-hex direct vs. SHA-256(passphrase)) and points readers to `src/auth/token-envelope.ts` for the envelope format.

## Decisions Made
- **IIFE over ternary.** The `!raw || !raw.trim()` guard plus the `deriveTokenKey(raw.trim())` call would have been a long ternary; an IIFE matches the local style precedent (oauthSessionTimeoutMs at line 46, oauthRefreshThresholdMs at line 56) and keeps the trim applied exactly once before delegating to the pure crypto module.
- **Trim before derivation, not inside.** Plan 01's `deriveTokenKey()` is a pure module that should not assume input normalization. Trim ergonomics belong to whoever reads the env var - this plan. That keeps the Plan 01 contract narrow and reusable for Phase 5 without surprise.
- **Sentinel-list isolation.** Added `MCP4_TOKEN_KEY` to `ENV_KEYS` so `beforeEach` unsets it. Without this, any developer with `MCP4_TOKEN_KEY` exported in their shell would get nondeterministic test results (the unset-test would suddenly fail). Mirrors the pattern already in place for the other 26 MCP4_* vars.
- **Test 7 (all-a hex) included.** Plan listed 7 tests; this one looked redundant with Test 4 (all-zero hex) at first glance, but it specifically guards against an implementation that calls `Buffer.alloc(32)` and accidentally passes Test 4 via lookalike output. Keeping it preserves the canary value.
